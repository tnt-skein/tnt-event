# tnt-event

Шина событий внутри узла Tarantool: приложение объявляет слушателя
и рассылает событие, а обработчик идёт в файбере этого же узла, без
спейсов, брокеров и сети. Подтверждение — то, что вернул обработчик;
событие, отправленное в транзакции `box`, уходит после фиксации.

```lua
local event = require('tnt.event')

event.listen('order.paid', function(message)
    local ok, reason = notify(message.body.order)

    if not ok then
        return nil, reason                       -- повтор с отсрочкой, потом зарыть
    end
end, { workers = 2 })

local sent, err = event.dispatch('order.paid', { order = 11 })   -- ULID либо nil, err
```

Зависимости: `tnt-message` (общая часть договора очереди: конверт, проверка
настроек и тела, приговор обработчику, область обработчика, крюки и ряды
метрик `message_*`), `tnt-must` (проверки аргументов), `tnt-clock` (время зарытого), `tnt-log` (журнал),
`tnt-storage` (отказ `overflow`) и `tnt-external` (подмена транзакции
в проверках).

## Зачем

Одно действие приложения часто тянет за собой несколько побочных:
сбросить кэш, записать аудит, разослать уведомление. Прямой вызов
заставляет отправителя знать всех получателей, ждать каждого и падать
от чужого исключения, а в транзакции первая же уступка получателя рвёт
её. Пакет делает шесть вещей:

- **У каждого слушателя своя очередь и свои работники**: медленный
  не держит быстрого, полный не отнимает событие у соседей.
- **Подтверждение — итог обработчика**: значение подтверждает,
  `nil, err` возвращает событие с отсрочкой, последняя попытка
  и `err.retriable == false` зарывают его в список зарытых.
- **Порядок держится ключом**: события одного ключа идут по одному
  и по порядку при любом числе работников.
- **В транзакции событие уходит после фиксации**, а при откате его нет.
- **Контекст едет с событием**: опознаватель запроса вызывающего
  приходит в обработчик заголовком.
- **Крюки отправки и обработки** дают трассу и замеры, не делая пакет
  зависимым от трассировщика.

Гарантия — не больше раза: очередь слушателя, отсрочка и зарытые живут
в памяти и пропадают с процессом.

## Установка

```sh
tt rocks install tnt-event --server=https://tnt-skein.github.io/rocks
```

Или из исходников:

```sh
git clone https://github.com/tnt-skein/tnt-event.git
cd tnt-event && tt rocks make
```

## Как пользоваться

| Вызов | Что делает |
|---|---|
| `event.listen(name, handler, opts)` | объявляет слушателя; настройки — `workers`, `capacity`, `max_attempts`, `backoff` |
| `listener:stop()` | снимает слушателя с шины; взятое дорабатывается, лежавшее в очереди пропадает |
| `event.dispatch(name, body, opts)` | рассылает событие и отдаёт его ULID; настройки — `headers`, `key`, `delay`, `id`, `timeout` |
| `event.dead()` | зарытые события, сто последних, копией |
| `event.hook(name, hook)`, `event.hooks()` | ставит, заменяет или снимает крюк; имена крюков по порядку |
| `event.status()` | счётчики шины, слушатели по именам с глубиной и работниками в обработке и отсрочке, число зарытых, крюки |
| `event.reset()` | снимает всех слушателей и забывает счёт |
| `event.features` | что шина умеет: `delay`, `key`, `transactional` — да, `ttl`, `priority`, `atomic` — нет |

Полная очередь слушателя — отказ `overflow` (`TntStorageFailure`
из `tnt-storage`, `retriable = false`), а не ожидание: `dispatch` зовут
и из `box.on_commit`, где ждать нельзя. Настройка, которой шина не
умеет, и тело не из простых данных — исключение на строке вызывающего:

```lua
event.dispatch('order.paid', { order = 11 }, { ttl = 60 })
--> error: настройки отправки: «ttl» — шина событий не умеет: событие ждёт
--> слушателя, пока жив процесс, и сроку жизни неоткуда взяться
```

## Проверки

```sh
make deps          # luatest, luacheck, luacov с cluacov и зависимости пакета в .rocks
make check         # форматирование, линт, проверки, покрытие с порогом 100 %
make mutants-all   # мутационное тестирование утилитой tnt-mutants из PATH, порог 100 % убитых
```

Счётчики сводки видны и рядами метрик договора очереди с именем события
меткой `destination`: `message_sent_total`, `message_send_failures_total`
(род `overflow`), `message_handled_total`, `message_worker_failures_total`,
`message_wait_seconds` и `message_depth` — сколько ждёт в полосах,
в обработке, в отсрочке и в зарытых.

Покрытие строк — 100 %, убитых мутантов — 100 % (47 проверок,
189 мутантов в двух модулях). Файберы, каналы и контекст в проверках
настоящие; транзакция вызывающего идёт двойником внешней зависимости,
а одна группа поднимает узел Tarantool: откат, фиксация и отказ полной
очереди внутри триггера фиксации, который не роняет процесс.
